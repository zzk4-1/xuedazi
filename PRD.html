01背景与目标

「找搭子」需求已被充分验证（小红书找搭子帖、校园墙、豆瓣小组撮合活跃），但撮合行为全部发生在通用社区里，无结构化筛选、无时间窗约束、无后续监督承接。存量产品各占一半：搭子类平台有社交无留存（撮合一次性），打卡工具有留存无社交（无真实同伴）。

产品决策：收窄到校园学习场景（考研 / 自习 / 四六级）作为唯一切入点——一个学校即一个天然密度池，「同目的地（同校）」与「同目标（备考）」在校园内同时成立，无需 LBS 基建。地点维度承担获客信任感，目标维度（进度与打卡）承担留存。

可观察结果：用户能够独立完成「发布搭子卡片 → 被同校用户响应 → 组队 → 连续多日互相可见打卡」的完整闭环，全程无需平台人工介入（认证审核除外）。

MVP 验证指标：假设唯一核心指标为发卡 48 小时响应率（招募中卡片在发布后 48h 内收到 ≥1 个申请的比例）。低于约定阈值则验证失败，收缩或更换场景，而非堆功能。

02产品契约

要素定义
主用户在校大学生，正处于备考 / 自习 / 语言考试周期内，想要同伴监督与陪伴
触发备考或自习周期开始时，主动寻找同校、同目标、时间窗重合的搭子
核心任务发布搭子卡片或响应他人卡片，组成小队后每日打卡互相监督
完成证据用户在小队页可见全体成员当日打卡状态与连续天数
共享业务对象搭子卡片（撮合载体）与小队（关系与打卡载体），两者 1 : 1
信任基础微信实名登录 + 学生身份人工审核 + 全量 UGC 内容安全检测 + 举报处理

03范围

P0 闭环（最小完整旅程）

1 登录选校微信授权登录，选择本校
→
2 学生认证上传证件照，人工审核通过后解锁发布/申请
→
3 发布卡片目标或地点 + 周期 + 每日时段 + 校内地点
→
4 广场响应本校用户按类别/时段筛选，留言申请
→
5 审批组队发起人通过申请，申请者进入小队并开放私聊
→
6 每日打卡小队内每人每日一次，成员互相可见
  • 入口条件：微信授权登录并完成本校选择。
  • 完成证据：小队页展示全体成员当日打卡状态。
  • 最重要失败的恢复路径：学生认证被拒 → 展示拒绝原因，允许重新提交（见 FR-02）。

P1（本期不做，接口留白）

P1目标进度百分比、小队打卡排行、搭子解散/毕业后的评价体系、跨校与旅行搭子扩展、订阅消息打卡提醒的精细策略。

明确不做（防止范围蔓延）

P0 排除匹配推荐算法（筛选即匹配）、LBS 地图与精确时刻区间计算、实时 IM（私聊为异步留言式）、积分与激励体系、任何变现功能、完整 Web 管理后台（MVP 用最小管理手段，见 FR-08）。

05功能需求

FR-01

登录与学校选择

触发：首次打开小程序。处理：微信一键授权登录（昵称头像取自微信资料），随后进入学校选择页——从内置学校白名单中选择本校。假设 首期白名单由运营手动维护，仅覆盖计划推广的学校；用户所选学校不在白名单时，可提交「求开放」反馈（记录学校名），页面提示「本校暂未开放」。

结果与状态：登录完成、学校落库，进入广场（访客态）。学校一经选择，认证通过前锁定。

FR-02

学生认证

触发：访客点击任何需要认证身份的动作（发布 / 申请 / 私聊 / 打卡）时引导进入；也可从「我的」主动进入。

处理：上传 1 张学生证或校园卡照片（提示遮挡身份证号等敏感信息）→ 状态置为审核中。假设 MVP 采用人工审核（开发者本人查看），承诺 T+1 内完成；不做 OCR 自动识别。

结果与状态：通过 → 已认证，解锁全部认证学生能力并推送结果通知；未通过 → 展示原因（如「照片模糊」「非有效证件」），可重新提交。未认证用户的所有写操作入口可见但点击即引导认证，不做隐藏。

FR-03

发布搭子卡片

触发：认证学生在广场点击「发布搭子」。

处理规则：

  • 类型：二选一——目标型（围绕一个要完成的成果）或地点型（围绕一个校内地点的共处时间）。类型影响详情页强调的字段，不影响权限与状态机。
  • 标题：必填，≤20 字。
  • 目标类别：必选枚举（考研 / 考公 / 四六级 / 期末自习 / 读书 / 健身 / 其他）。
  • 周期：开始日期 ≥ 今天；结束日期 > 开始日期且 ≤ 开始 + 180 天。假设 上限 180 天覆盖考研备考周期并防止僵尸卡片。
  • 每日时段：多选标签，至少 1 项——清晨（6–8）/ 上午（8–12）/ 下午（12–18）/ 晚上（18–23）。决策 用标签而非精确时刻区间，MVP 仅用于筛选展示，不做重合度计算。
  • 校内地点：必填，从本校常用地点标签中选择或自定义文本（如「东图书馆三楼」）。地点型卡片此字段为卡片主体。
  • 想找几位搭子：1–10，不含自己。卡片「目标人数」= 该数值 + 1（含队长），广场展示「已加入 1/4」即队长已占 1 席。
  • 描述：选填，≤200 字。
  • 数量限制：同一用户最多同时持有 2 张「招募中」卡片。假设 防刷屏，同时保留「考研 + 跑步」双搭子场景。

结果与状态：全部 UGC 字段先过内容安全检测（见共享规则 R-2），命中则发布失败并提示修改；通过后卡片以「招募中」进入广场，小队同时预创建，队长为第 1 名成员。

FR-04

搭子广场（浏览与筛选）

触发：任意用户进入首页。

处理规则：默认展示本校 + 状态为招募中的卡片；筛选维度为目标类别（单选）、每日时段（多选，卡片需包含全部所选时段）；排序固定为发布时间倒序；卡片项展示：类型标、标题、类别、已加入人数 / 目标人数、时段标签、校内地点、剩余招募天数。跨校内容 MVP 一律不可见。

结果与状态：筛选无结果时展示空态并引导放宽筛选或发布自己的卡片；点击卡片进详情（含完整描述、队长信息、已加入成员、申请按钮）。已满员 / 已结束卡片可看不可申。

FR-05

报名申请与审批

触发：认证学生在「招募中」卡片详情点击「申请加入」。

处理规则：申请需附一句话留言（必填 ≤50 字，如自我介绍与节奏匹配说明）；同一用户对同一张卡片只能存在一个待处理 / 已通过的申请；队长在小队页与通知中看到新申请。

结果与状态：队长通过 → 申请者加入小队、卡片已加入人数 +1、双方自动建立私聊会话；若人数达目标人数，卡片自动转「已满员」，其余待处理申请批量置为已失效。队长拒绝 → 申请者收到结果，可再对其他卡片发起申请。审批无时效约束，但卡片到期时未处理申请自动失效。

FR-06

小队与每日打卡

触发：小队成员进入小队页。

处理规则：小队页展示成员列表（头像、昵称、队长标、连续天数、今日是否已打卡）；成员每日可打卡 1 次——文字必填 ≤100 字 + 可选 1 张图，全部过内容安全检测；连续天数按自然日连续计算，断签即清零重计；当日 24:00 后不可打卡，不支持补签 假设。

结果与状态：打卡成功后本人与全体成员立即可见；卡片「已结束」后小队转只读，历史打卡可查看。成员可退出小队（已加入人数 −1）；已满员卡片因成员退出回到「招募中」并重新接受申请；队长退出前必须先转让队长（转让给任一成员），防止小队无主。

FR-07

私聊（异步留言式）

触发：报名申请通过后，双方自动获得会话；也可在小队成员列表内向队友发起。

处理规则：会话仅限通过申请建立的关系，不可向陌生用户直接发起；消息为文字（≤200 字）与图片，逐条过内容安全检测；不承诺实时送达，以未读红点提示新消息。决策 MVP 不做实时 IM 与推送依赖，降低开发与合规成本。

结果与状态：消息不可撤回（MVP）；任一方被举报封禁后会话冻结只读。

FR-08

举报与安全处置

触发：用户在卡片详情、用户资料页、私聊会话点击「举报」。

处理规则：举报理由从预设枚举选择（虚假身份 / 骚扰 / 广告营销 / 违规内容 / 其他）+ 可选补充说明；举报不影响被举报对象的使用，直至管理员处置。

结果与状态：假设 MVP 管理端为最小管理手段（数据库直接操作），无自助后台。管理员可：下架卡片（状态 → 已下架，发布者与成员可见原因）、封禁用户（封禁后不可发布 / 申请 / 打卡 / 私聊，已进小队保留成员身份但转只读）。处理结果反馈举报人。

R-2 内容安全（合规硬性要求）

所有用户产生内容——卡片全部文本字段、申请留言、打卡文字与图片、私聊消息——在发布前调用微信内容安全检测接口（文本 / 图片各对应接口）。命中违规：该次发布失败，明确提示用户修改；不静默丢弃、不先发后审。

R-3 通知

假设 MVP 通知手段为小程序内红点 + 微信订阅消息（需用户主动订阅）：新申请（通知队长）、申请结果（通知申请者）、认证结果、卡片被下架。不做推送策略的精细化运营。

R-4 时间与到期

日期均按北京时间自然日；卡片到期（结束日期 24:00）由系统自动转「已结束」；未处理申请批量置为已失效；「已结束」小队的打卡入口关闭、历史保留。连续天数以打卡记录的自然日连续性为准，时区不引入任何修正。
